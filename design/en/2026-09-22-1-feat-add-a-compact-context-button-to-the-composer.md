# 2026-09-22-1-feat-add-a-compact-context-button-to-the-composer

## Direct Reason

Compacting the context was reachable only by typing the `/compact` command; the composer offered no entry point.

## Solution

Registers an icon-only button at the right end of the composer tool row's left group (after `+`, the paperclip, and the mode selects). A click opens a confirmation popover, and only its confirm submits the command through `ctx.remote.commands.execute(sessionId, '/compact', [])`; an outside click or Escape cancels. The button is disabled while the session turn is running and while a submission is in flight; `mousedown` suppresses the default focus so the caret stays in the editor, as every other button in that group does. A new `compact-button` feature module carries it and takes a Settings toggle.

## Approach

**Conclusion**: reuse the official command channel to run the existing `/compact`; disable the button while running on the premise that manual compaction requires an idle agent; and, because compaction cannot be undone, gate the submission behind a confirmation popover.

Causal chain:

- The goal is "the effect is the same as the compact command". Two routes reach it: call the compaction capability directly, or submit that command. The command wins because it *is* the definition of "same as the command" — calling the capability directly would mean re-copying the whole branch set (no compactable history, busy, summary failure, and the rest), and one missed branch stops being equivalent.
- Submitting the command needs a command channel. An official precedent exists: `ui-plan`'s Plan control leaves plan mode through `ctx.remote.commands.execute(sessionId, '/plan off', [])`, so this follows it, adding no service and touching no dsh source.
- That choice carries one further constraint: the Host writes the command's lifecycle into the session log (`command/run` / `command/done`) and the outcome renders as a conversation node, and the command palette itself never echoes outcomes either. So the button only submits and never restates success or failure; restating it would put one fact on two surfaces.
- Why the confirmation popover: the first version submitted on the first click, and the user reported "one click compacts it straight away, which feels risky — a single slip would have hit it". Compaction rewrites session history and has no undo path, so one stray click is irreversible, and an explicit confirmation belongs before the submission. The popover carries only one confirming question and one confirm button; cancelling goes through an outside click or Escape, so a small icon button does not grow two extra controls. The copy was first written as a statement of consequence ("older history is replaced by a summary") and the user replied that "the popover should be a confirmation interaction"; it is now the question "Confirm compaction?" with the button reading "Confirm" — a statement reads as a warning label rather than asking the user whether they are sure.
- Why the running state disables it: manual compaction requires an idle agent (`command-compact` returns a failure line for a busy one). Left live, a click would only produce an inevitably failed node — handing the user an operation known in advance to fail.
- Why `conversation.input.left`: that list slot renders at the end of the left group, which is "the right of the bottom-left area", and it had no occupant, so `order: 100` collides with nobody.
- Why the glyph is supplied by the user: the official icon library has no glyph meaning compress, and both official picks were misread. `IconApiOutline14` (the glyph the transcript's compaction marker draws) is a rounded box holding `>` and `_` — a terminal prompt — and the user reported it "looks like SSH"; swapping to `IconEnhanceOutline16` gave four shrinking bars, which the user read as "a paragraph". Both mistakes came from choosing by icon name or precedent instead of by the drawn shape. My own hand-drawn version — a centre bar with arrows pressing toward it — was then called "too odd"; the user's first supplied shape was then rejected as "smaller and unreadable", because I had set it to 14px. The shipped shape is the user's second one at 16px (the official icon set's default). That 14px came from the `size={14}` its two row neighbours use, but they were chosen for sparse artwork; this one has denser strokes whose detail smears together at 14px. Inline SVG has precedent: `session-id-copy`'s `HashGlyph` exists because the official set has no hash glyph, and `d` is not a copy attribute (absent from `COPY_ATTRIBUTES` in `scripts/verify-client-ui-i18n.ts`), so the gate does not object.
- Why it is a toggle: this plugin's other five features are all Settings-switchable modules, and `modules` is constrained by `Record<keyof Config, ModuleEntry>`, so a new module joins the existing mechanism with no change to the Settings page code.
- A correction to the toggle-row order: `MODULE_ORDER`'s comment claims it is ordered by position, but the actual order had already drifted when `session-id-copy` was added (commit `4c41cbb`) — the header's `session-id-copy` sat after the two composer-row entries; this change appended `compact-button` in the same place without re-checking. After the user raised it, the list is ordered by where each module sits: Session header → composer row (left group `compact-button`, right group `provider-label`, `model-picker`) → Settings page (`open-dsh-folder`, `settings-frame`). The feature tables in `README.md` / `README.zh.md` carried the same stale order and were adjusted with it.
- Why the popover must mount in the frame it opens: `useAnchoredPosition` reads `panelRef` for its dimensions during that frame. The first version gated the portal on `{open && position && ...}`, so on the first open `position` was still `null`, the panel was not mounted, its height therefore read as zero, the `height > 0` viewport clamp was skipped, and the `ResizeObserver` was never created (`panel === null`) so no correction ever arrived — the popover grew downward off screen. It now renders on `{open && ...}` at a hidden measuring position (the purpose of the official `Menu`'s `MEASURE_STYLE`) and is placed once coordinates exist.
