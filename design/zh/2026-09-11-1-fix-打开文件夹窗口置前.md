# 2026-09-11-1-fix-打开文件夹窗口置前

## 直接原因

「打开 .dsh 文件夹」在 Windows 上打开的窗口经常落在浏览器窗口下面。Windows 只允许前台进程、它启动的进程、或刚接收过输入的进程激活窗口；本插件的调用链是浏览器 →（RPC）→ dsh web 宿主（后台进程）→ powershell.exe → explorer.exe，三个条件都不满足，因此新窗口不被允许提到前台。

dsh 共享的 `@deepseek-ai/dsh-native-command` 的 `openNativePath` 在这个平台分支上只执行 `Invoke-Item`，未做前台激活处理，所以 dsh 自带的「打开配置文件/文件夹」同样会被压到后面。

## 解决方案

Windows 分支不再调用共享的 `openNativePath`，改为自写 PowerShell（`src/open-dsh-folder.ts` 的 `windowsOpenScript`）：

1. `Invoke-Item -LiteralPath` 打开文件夹；
2. 轮询 `Shell.Application` 的 `Windows()`，按 `LocationURL` 匹配该文件夹的 explorer 窗口并取 `HWND`（explorer 异步建窗，最多等 3 秒）；
3. 通过 `keybd_event` 合成一次 Alt 按放，使本进程成为「最近输入拥有者」，取得激活资格；
4. 对该 `HWND` 调用 `SetForegroundWindow` 置顶。

未匹配到窗口时按成功退出（文件夹已打开，只是无法定位其窗口）。非 Windows 平台继续走共享的 `openNativePath`。

## 思路

- 复用 harness 自身在原生文件夹对话框（`packages/host/directory-picker-native`）里验证过的做法：合成 Alt 按放让后台进程取得激活资格。区别是那个对话框由本进程创建，而资源管理器窗口归 explorer 所有，因此必须再显式对其 `HWND` 调用 `SetForegroundWindow`。
- 脚本经 `runNativeCommand`（`execFile`，无 shell）执行；路径以 PowerShell 单引号字面量注入，内部单引号翻倍，避免注入与转义问题。
- 实测方式：让记事本占住前台后，以生产路径（`execFile` + `-NoProfile -Command`）执行生成脚本，再读 `GetForegroundWindow()` 与目标 `HWND` 比较，确认前台已切换。
- 侧写（工程结构）：Host 与 Client 两面共享的类型提取到 `src/types.ts`（仅类型、无运行时代码），并按仓库规范把单个 tsconfig 拆为 `tsconfig.host.json` + `tsconfig.client.json` 两个 leaf 加 solution-only 根。原先整包按 Client 面编译，宿主半边看不到 node 全局声明，无法使用 `process.platform`。
